Identify a known-good release

Record the date, source revision, tested web URL, OS and Python versions, USB adapter ID and GPIB resource. Save checksums of the exact app, dashboard templates, documentation, pinned requirements, systemd unit, nginx site, and udev rules. Keep the record with each backup.

Clean installation was verified in HTTPS and HTTP-only modes on fresh Raspberry Pi OS Lite (64-bit). Backup restoration is a separate procedure. Verify it on a spare card before relying on a restored controller.

For each known-good deployment, record its test date, controller hostname and IP address, OS and Python versions, USB adapter ID, and GPIB resource. Record which dashboard and documentation routes were verified, and whether a bare-card restore and control commissioning have been tested. Treat older archives as historical until checked.

Create a private backup

Save the block as backup.sh. Run it when no one is editing presets or deploying changes. An HTTPS archive can contain TLS private keys and password hashes. HTTP-only installations omit those files. Store it in a root-only directory and copy it to protected storage off the Pi. This is an application and configuration backup. Keep a separate SD-card image if you need the entire operating system.

#!/usr/bin/env bash
# Run as root. Store the resulting archive and checksum privately.
set -euo pipefail
umask 077
dest=${1:?Usage: sudo bash backup.sh /absolute/private/backup-directory}
[[ "$dest" == /* ]]
install -d -m 0700 "$dest"
cd /
items=(
  home/pi/hp6033a/app.py home/pi/hp6033a/templates
  home/pi/hp6033a/docs home/pi/hp6033a/static
  home/pi/hp6033a/requirements.txt home/pi/hp6033a/deploy
  etc/systemd/system/hp6033a.service
  etc/nginx/sites-available/hp6033a
  etc/udev/rules.d/99-usbgpib.rules
)
for item in home/pi/hp6033a/config.json home/pi/hp6033a/.control_auth_mode \
            home/pi/hp6033a/.control_htpasswd etc/nginx/hp6033a.htpasswd \
            etc/nginx/ssl/hp6033a.crt etc/nginx/ssl/hp6033a.key \
            home/pi/hp6033a/scripts \
            etc/systemd/system/hp6033a.service.d; do
  if [[ -e "$item" ]]; then items+=("$item"); fi
done
bundle=$(mktemp -d "$dest/hp6033a-$(date -u +%Y%m%dT%H%M%SZ).XXXXXXXX")
tar -czf "$bundle/controller.tar.gz" -- "${items[@]}"
(
  cd "$bundle"
  tar -tzf controller.tar.gz > files.txt
  sha256sum controller.tar.gz > SHA256SUMS
  sha256sum -c SHA256SUMS
)
printf 'Backup saved in %s\n' "$bundle"

The backup omits the virtual environment, logs, and historical development archives. Rebuild the virtual environment from pinned requirements. If your installation uses extra certificates, nginx includes, external device configuration, or other service overrides, record and back those up separately.

Restore onto a replacement SD card

  1. Image a spare card using the Installation page. Use a separate IP until you are ready to switch over. Keep the supply output off.
  2. Use your own trusted backup. In the private backup folder, verify the checksum and inspect the file list before extracting to an empty root-only staging directory.
# Run in a root shell inside the trusted backup directory.
sha256sum -c SHA256SUMS
tar -tzf controller.tar.gz
stage=$(mktemp -d /root/hp6033a-restore.XXXXXXXX)
tar -xzf controller.tar.gz -C "$stage" --no-same-owner --no-same-permissions
printf 'Restore staging: %s
' "$stage"
  1. Use the recorded source revision and follow the Installation page on the replacement Pi. Choose the recorded connection mode. For HTTPS, use password protection during initial commissioning. Use HTTP-only mode on a trusted LAN.
  2. Compare the backed-up config.json with the replacement configuration. Restore the presets and display labels. Verify the VISA resource on the replacement adapter before restarting the service.
  3. For HTTPS, keep the new controller credentials or restore both matching credential files together with the permissions shown below. Skip the credential commands for an HTTP-only restore. The example assumes the controller user is pi. Use TLS material that matches the replacement address.
# Run as root with $stage from the extraction step.
install -o pi -g pi -m 0600 "$stage/home/pi/hp6033a/.control_htpasswd" /home/pi/hp6033a/.control_htpasswd
install -o root -g www-data -m 0640 "$stage/etc/nginx/hp6033a.htpasswd" /etc/nginx/hp6033a.htpasswd
nginx -t
systemctl reload nginx
  1. Use the installation verification script and confirm read-only GPIB measurements. Confirm the old Pi is offline before reusing its address.
  2. For HTTPS, review the saved authentication policy in dashboard Setup after commissioning. HTTP-only operation uses password-free controls and command-line updates.

Maintenance and rollback

Run the health checks before and after updates. For a failed app update, recover the app and matching dependency versions from the same known-good archive. Preserve newer settings only if compatible. Take a private backup of the current state before replacing files.

Confirm the physical output is off before stopping or restarting the service. Validate any nginx change with sudo nginx -t before reload. After rollback, verify all web routes and GPIB status with the same checks used during commissioning.

The backup script and staged restore procedure are documented for testing on a spare Pi. A verified rollback requires the checksum, successful extraction, and a commissioning record for the restored release.

In-place updater recovery

The updater prints its private ~/.hp6033a-backup-* directory. Keep it until the update has been commissioned. It contains the previous application directory after success, an application archive without the virtual environment, a system archive with the prior unit, Nginx site and relevant security files, and update.json describing the runtime decision. Run sha256sum -c SHA256SUMS inside the private directory before using either archive.

After failed activation the updater restores the previous app and checks the controller over its installed HTTP or HTTPS protocol. An interrupted update or unsuccessful rollback leaves ~/.hp6033a-update.pending pointing at the backup. Keep that file until recovery has been verified. Inspect sudo journalctl -u hp6033a -n 80 --no-pager and confirm the instrument output is off before stopping the service for manual recovery.

  1. Inspect the backup. previous is the original tree if the switch took place and rollback has not already moved it back. If the active app is already the original tree, leave it in place. Keep the candidate and failed trees until you locate the original virtual environment.
  2. If restoring previous, stop hp6033a.service. Move the current app aside. If update.json says the virtual environment was reused and previous/venv is absent, move the original venv entry back from the current, candidate or failed tree. Preserve symlinks and leave any absolute runtime target at its original path.
  3. Move previous back to ~/hp6033a. Start only hp6033a.service, verify the status at the controller’s installed URL, then remove the pending marker. If the original tree or runtime cannot be located, preserve the archives and use the replacement-install procedure. The updater leaves system configuration in place, so the system archive is for separate recovery if needed.

Dashboard update recovery

The Software Updates panel shows a job ID. The helper records its job status across an application restart. For a failed job, inspect its log and the helper service journal from an administrator account. Substitute the displayed job ID.

sudo journalctl -u hp6033a-update.service -n 80 --no-pager
sudo less /var/lib/hp6033a-update/JOB_ID/worker.log

Web jobs store the system archive and its checksum under the root-only job directory. The app backup under ~/.hp6033a-backup-* contains system-backup.json pointing to that archive. Check both sets of checksums before restoring. If the dashboard reports recovery required, follow the in-place updater recovery procedure. Keep the pending marker until the old application and its HTTPS status are verified.

If initial provisioning failed, inspect the helper journal and unit status. The main controller can continue operating without the update helper. Preserve /var/lib/hp6033a-update, which contains the administrator credential hash, job records and private system backups.
